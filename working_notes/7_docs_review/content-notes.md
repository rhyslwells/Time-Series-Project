Reading these as time series documents rather than as web pages: the writing is better than the methodology. Several pages are well-argued and a few contain domain judgments that are genuinely good. But there are load-bearing methodological problems, and a couple of places where the docs give advice that is wrong for this data specifically.

The three that matter most
1. There is no baseline anywhere, so none of the numbers mean anything.

metrics.md states thresholds in absolute terms — "MAE < 0.5 kWh good, > 1.5 poor". For a series with strong daily seasonality at s=48, the reference point is seasonal naive, ŷ_t = y_{t-48}. On clean synthetic data with a hard-coded daily profile, seasonal naive will be very strong, and it is entirely plausible that SARIMA and LightGBM do not beat it. Without that number on the page, a reader has no way to know whether an MAE of 0.4 represents skill or represents a model that has learned less than copying yesterday.

This is also the fix for the MAPE problem. The docs call MAPE "the right metric for comparing forecast quality across differently-sized assets" — that's the standard trap. MAPE is undefined at zero, unstable near it, and asymmetric (it penalises over-forecasting more than under-forecasting). For solar_battery assets whose values cross zero, it is not merely unstable, it is meaningless, and the suggested max(|y_t|, ε) patch silently changes the metric so that cross-asset comparison — the reason it was chosen — no longer holds. MASE is the correct instrument: scale-free, defined at zero, and by construction it is the skill ratio against seasonal naive. One metric closes both gaps. Note archive/TimeSeries/Forecasting/Forecasting_Baseline.py exists, so the idea was in the repo and never reached the docs.

2. The documented workflow tunes on the test set.

framework_usage.md prescribes: compare models → grid search → refit → compare before/after. But ModelTuner (ts_model_framework.py:405-430) fits on y_train, evaluates every trial against y_test, and ranks by RMSE on y_test. Hyperparameters are therefore selected on the same data used to report final performance, and the closing print(f"RMSE: {metrics.rmse} -> {final_metrics.rmse}") reports an improvement that is guaranteed by construction. The reported metrics are optimistically biased and the size of the bias grows with the grid.

Underneath this sits a second issue: the entire evaluation rests on a single fixed split. On 14 days, one 10/4 split gives one realisation, and the ranking between three models will be substantially noise. Rolling-origin evaluation is the standard remedy and index.md already lists "walk-forward validation" as a concept explored — it isn't, anywhere. archive/TimeSeries/out-of-sample rolling forecast evaluation.py again suggests this was known.

3. No documented model can represent the weekly cycle that the data provably contains.

generate_raw_data.py:20 hard-codes a 1.2/0.8 weekday-weekend factor for EV assets, and synthetic_metering_data.md documents a 20-30% weekday-weekend difference as a headline characteristic. Yet:

SARIMA takes a single seasonal period; the recommended s=48 captures daily only.
LightGBMModel._create_features (:209-224) builds lags plus hour_of_day, with no day-of-week feature, and default lags [1, 2, 48, 96] reach back two days.
Holt-Winters takes one seasonal_periods.
So a known, documented, deliberately-injected pattern is invisible to all three default configurations. This is the largest substantive gap. The standard treatments are Fourier terms at both periods with ARIMA errors, MSTL, or simply a day-of-week feature for the tree model. And the catch: with 14 days you have two weekly cycles, so weekly seasonality is barely estimable at all — which means the honest conclusion is that this dataset cannot support the weekly component, and the docs should say so rather than recommending s=336 and lag 336 as if they were available options.

Advice that is wrong for this data
Multiplicative seasonality on net exporters. models.md:50 suggests seasonal="mul" as a coverage fix, and framework_usage.md:96 puts "mul" in the recommended grid for both trend and seasonal. Multiplicative components require strictly positive data. The solar_battery assets are net exporters that cross zero, so this will fail or return nonsense for seven of fifteen assets. It is recommended twice with no caveat.

The default is over-differenced. models.md gives SARIMA(1,1,1)(1,1,1,48) as the starting point, applying both non-seasonal and seasonal differencing. synthetic_metering_data.md:132 states the data has "no trend or drift" — and load data is generally mean-reverting in level anyway. Applying d=1 to a series with no trend inflates the innovation variance and induces spurious negative MA structure. D=1 is defensible here; d=1 probably isn't. The two pages contradict each other on a modelling default.

Relatedly, "Expect φ₁ ≈ 0.7-0.9 — energy usage persists strongly" describes the autocorrelation of the level. With d=1 the AR coefficient is estimated on Δy, where values are typically much smaller and often negative. As written it will lead a reader to think a correctly-fitted model is broken.

"Exploding width" is diagnosed backwards. diagnostics.md:31 flags intervals widening with horizon as a failure mode, attributes it to "naive error propagation (std growing with √horizon)", and prescribes capping the width. But for an integrated process, h-step forecast variance genuinely grows roughly linearly in h, so std ~ √h is the correct behaviour, not an artefact — it's what SARIMA's own conf_int produces. And capping produces miscalibrated intervals by construction, which is the failure the rest of the page is trying to prevent. The real problem in this codebase is the opposite: ExponentialSmoothing (:175) and LightGBM (:273) hold width constant across a 192-step horizon.

The LightGBM interval warning is right for the wrong reason. models.md:61 attributes narrow intervals to the point forecast being "systematically optimistic". The actual cause is that a one-step in-sample residual std is applied to a 192-step recursive forecast. forecast() (:250-258) feeds predictions back as inputs, so past step 96 every lag feature is itself a prediction and errors compound — while the interval width never moves. The stated cause sends a reader looking for bias when they should be looking at the forecasting strategy (direct multi-step, or DirRec, instead of recursive).

What the toolkit is missing
Proper scoring rules. The docs care specifically about the width-versus-breach tradeoff — models-decisions.md:11 argues coverage should beat RMSE for flexibility commitments, which is a correct and non-obvious judgment. But coverage alone is gameable: you can hit 80% by making intervals enormous. The interval (Winkler) score and pinball loss combine width and breach into a single number and are exactly the object this argument wants.
Information criteria. The "complexity budget: parameters under n/10" heuristic in models.md:34 isn't a standard rule. AIC/AICc/BIC are how ARIMA orders are selected, AICc specifically at these sample sizes. Nothing on the site mentions them, though archive/.../Forecasting_AutoArima.py exists.
Stationarity testing. The docs say differencing achieves stationarity and that troubleshooting should "check stationarity", but never say with what. ADF/KPSS for d, and a seasonal-strength or OCSB/Canova-Hansen criterion for D. Given the over-differencing point above, this omission has a direct cost.
STL. Listed on the home page as a core task, absent everywhere. It's the natural tool for this data, and it supplies the missing definition in asset_profiling.md, which lists "seasonality strength" as its primary discriminator without ever defining it. The standard definition is F_S = max(0, 1 − Var(R)/Var(S+R)) from an STL decomposition — that one formula makes the profiling page's central claim operational.
Hierarchical reconciliation. forecast_products.md:55 makes the correct point that portfolio uncertainty depends on error correlation. The established next step — bottom-up versus top-down versus optimal reconciliation (MinT) — is the standard framework for a multi-asset portfolio and isn't mentioned.
Horizon as a first-class parameter. Everything is written as though there is one forecast. Day-ahead (h=48) and intraday (h=1-6) are different problems with different winners, and MAE at h=1 versus h=192 differs substantially. Every threshold table in metrics.md should be horizon-qualified. For an energy flexibility application, where market gate closure sets the horizon, this is a real framing gap.
Heteroskedasticity. The dominant feature of load-forecast residuals is that variance scales with level and time of day. diagnostics.md identifies "flat width" as a symptom but never names the cause or the remedies (variance-stabilising transform for strictly positive assets, conditional variance modelling, or direct quantile regression).
Two subtler points
The leakage caveat in feature_engineering.md:72-79 is the best methodological writing on the site — it correctly identifies same-day leakage and prescribes the lag. It's incomplete in one way worth adding: lagging by one day is sufficient only for h ≤ 48. For a 4-day-ahead forecast, days 2-4 have no observed daily metrics available at forecast time, so the features would have to be forecast themselves or held at the origin value.

Anomaly detection via residuals (forecast_products.md:41-43) has a circularity the page doesn't flag: you need a trusted model to detect asset anomalies, but the model was fitted on data containing them. And because residuals are heteroskedastic, a fixed threshold will flag peak hours preferentially — residuals need standardising by time of day before thresholding.

What's genuinely good
Worth saying plainly, because the fixes above shouldn't imply a rewrite. The good/failure-case structure in diagnostics.md is how diagnostic documentation ought to be written. The RMSE/MAE ratio as an outlier tell is a nice, underused heuristic. The argument that calibration should outrank point accuracy when a forecast feeds a flexibility commitment is a correct domain judgment that most general-purpose forecasting docs get wrong. And the forecast-as-distribution framing in forecast_products.md, with the insistence that downstream consumers receive expected/conservative/uncertainty as three separate numbers, is the right architecture.

How this folds into the plan
Most of it lands in C4 (theory spine), which grows considerably: a baseline-and-skill section in metrics.md, MASE and interval score added, horizon qualification on the threshold tables, the multiple-seasonality problem stated honestly against a 14-day dataset, and the SARIMA defaults reconciled with the "no trend" claim. The seasonal="mul" correction and the LightGBM recursive-forecasting explanation belong in Phase 3-4 with the other code-contradiction fixes, since they're wrong rather than merely incomplete. The tune-on-test issue is a code problem — it goes in the Phase 6 report alongside the MAPE scaling, and it's the one I'd rank first there.

Whether to add a seasonal-naive baseline to the framework itself is a real scope decision rather than a documentation fix, so I'd want your call before touching it.
